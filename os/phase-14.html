Automation Tier Architecture — Decision Locked This Phase
CoWork Scheduled Tasks — Proof of concept only
Good for testing ideas quickly. Not for production business operations. Rate-limited, network-constrained, and disconnected from the dispatcher's audit trail. The weekly advisory board review that lived here is now being moved to the OS dispatcher.
Claude Code Routines — Claude-internal ops only
Skill audit, session summary, memory management. Work that lives inside Claude's own operation — not business workflows. Does not belong in the dispatcher.
Northlight OS Dispatcher (Railway) — All business automation
One log, one place to debug, one deployment. If the work is about running the business, it belongs here. Morning scan, marketing pipeline, PMO, advisory board review — all in the dispatcher, none in CoWork or Code routines.
Key Decisions
Batch endpoint auth: Authorization header, not cookie session
Claude Code sessions don't have browser sessions. A separate DISPATCHER_API_KEY header (matching the existing schedule-social pattern) lets any environment with curl call the endpoint without OAuth. The route double-checks the key; requireAuth() mirrors it as a safety belt.
Advisory board digest: Slack only, drop Gmail draft
CoWork's version created a Gmail draft and then pinged Slack to go check it — one extra step with no benefit. Elizabeth: "I'd rather read it exactly in Slack." Full digest now posts directly to #chief-of-staff; the Gmail draft step was removed entirely.
Tag-based routing: extractSkillTag() replaces isAssignedToClaude()
The Claude ClickUp account (member ID 101209983) was the routing gate — fragile, because closing the account or changing username breaks routing silently. skill:* tags are explicit, visible in ClickUp, and survive any account change. The marketing pipeline already used tags; the general dispatcher now matches.
Individual op failures don't abort the batch
A tag call failing on task #7 shouldn't block the status update on task #9. Each op is independently try/catched, logged, and returned in the results array. Callers can inspect per-op success/failure without the whole batch going silent.
listDriveFolder() added to drive-store.js, not a one-off
The advisory board review needed folder scanning, not just file reads. Rather than inline it, the function was added to the shared drive-store module so any future skill can enumerate a Drive folder by ID without reimplementing the API call.
Learnings
Two separate ClickUp rate-limit systems — know which you're hitting
The ClickUp real API (100 req/min, Business plan) and the MCP connector quota (50 calls/day, Free Forever plan) are completely independent systems with different error formats and cooldown durations. A "wait 1152 minutes" error from the MCP connector is not a ClickUp API rate limit — it's the connector's own quota layer. Treating them as the same problem wastes time on the wrong fix.
Reconnecting a broken MCP connector makes things worse, not better
After the connector entered a "multiple workspaces" broken state, each reconnect attempt generated a new broken state (empty workspace list, undefined workspace_id parameter). The correct call was to stop touching it and build an alternative — the batch endpoint. When a connector is in broken state, treat it as out of service and route around it.
Three-minute cache turns 30+ API calls per dashboard load into 0
getAllTasks() previously ran a full workspace traversal on every /api/data hit. Three dashboard opens in two minutes = three full traversals. A short in-memory cache with a cache bust on writes is enough to eliminate almost all redundant API calls without affecting the user's experience of data freshness.
The advisory board review task is a CoWork-to-OS migration, not a net new build
The skill logic was already validated in CoWork — scanning Drive, extracting action items, creating tasks, posting to Slack. Phase 14 was the production migration: same logic, proper infrastructure (auth, scheduler, Drive state, real ClickUp API, no connector quota). CoWork as proof-of-concept, OS as production is the right sequencing pattern.
Assignee-based routing is an invisible dependency
isAssignedToClaude() worked fine until it didn't — the Claude ClickUp account's username and email were the only thing routing tasks to the dispatcher. Closing or renaming that account would have silently broken the morning scan with no error. Explicit skill: tags are visible in ClickUp, survive account changes, and align with how marketing pipeline routing already worked.
